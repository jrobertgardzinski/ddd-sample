# Review of microservice-security — 2026-09-08/09

Whole-repository review of `main` at `33a17d9` (2026-09-06, "SetSetting: any live rule set by its key through the rule's own gate"). Working tree was clean throughout; nothing in the repository was changed by the review. CI on main was green.

## How this review was made

Three sequential passes, one agent at a time:

1. **Find** — 12 reviewers, one per area (domain, config, authentication/sessions, MFA/step-up/federation, registration/account/settings/roles, HTTP edge, wiring/OAuth/JWT, persistence/outbox/saga, specs and tests, UI, docs/build/CI, attacker walk over every route). 190 raw findings; 47 were the same defect seen from several areas and were merged, leaving 143.
2. **Refute** — 12 skeptics, one per area, each told to *refute* every finding: re-read the code, find the missing check, the test that already pins it, the convention that makes it deliberate. Most ran targeted test classes or one throwaway test to decide.
3. **Reproduce** — for every finding still HIGH or CRITICAL after the skeptic, a third independent agent started from zero and tried to reproduce it with a real test (embedded server, in-memory adapters, Testcontainers where Docker was reachable).

Result of the 143: **1 CRITICAL, 10 HIGH, 27 MEDIUM, 101 LOW, 4 refuted**. Nine of the eleven CRITICAL/HIGH items were reproduced with a running test; the other two (dependabot auto-merge, sign-in form retention) were traced against live GitHub state and code respectively.

Owner's conventions were given to every agent as non-findings (underscore steps, no null checks below infrastructure, no javadoc on use cases, dotted config keys, the one-snapshot live level, ADMIN may set any live key, Kafka behind the outbox, Rebuild-level spec literals, `Source` = IP, dissolved modules, quiet refusal on `/register`, live MFA compliance in the filter, `security-application` has no `src/main`).

Severity after verification: CRITICAL = exploitable with what an attacker plausibly has; HIGH = wrong behaviour on a realistic path or a real security weakening; MEDIUM = latent bug, race, or gap that needs one more precondition; LOW = hygiene, drift, naming, missing test.

## CRITICAL

### MFA-1 — a `webauthn.create` proof is accepted at sign-in and step-up: the passkey factor is bypassable with the password alone
`security-system/.../mfa/WebauthnFactor.java:110`

`WebauthnFactor.verify()` trusts the client-supplied `clientDataJSON.type`. A `webauthn.create` envelope is accepted whenever it carries non-null `publicKey` and `credentialId` strings, the origin is on the allow-list and the echoed challenge hashes to the stored code hash. The challenge nonce is public by design (it is the `challengeData` in the 202 body), so the branch never inspects the enrolled key and never verifies a signature. The same `verify()` is reached from `/authenticate/factor` (via `MfaChain`) and `/account/step-up/factor` (via `StepUp.submitFactor`).

**Reproduced** over HTTP (embedded server, `test` env): enrol a real P-256 passkey honestly; then, holding only the password, `POST /authenticate` → 202 with the nonce; `POST /authenticate/factor` with `proof={type:webauthn.create, publicKey:"x", credentialId:"y", clientDataJSON:b64({type:webauthn.create, challenge:<nonce>, origin:http://localhost:4200})}` → **200 with an access token**, `/me` answers the victim. `MfaHttpTest` (5/5 green) only ever submits `webauthn.get`.

**Fix (system layer, `WebauthnFactor`):** accept the `create` branch only while the enrolment is pending (`enrolment.secretMaterial()` blank — the sentinel `beginEnrolment` sets); a stored factor always carries `{credentialId,publicKey}`, so at sign-in/step-up the branch is refused and control falls through to the `webauthn.get` signature check. Cleaner: split the port into `verifyEnrolment(...)` (used only by `EnrolFactor.confirm`) and `verify(...)` that hard-requires `type == "webauthn.get"`. Add a `WebauthnFactorTest` case and an `MfaHttpTest` case submitting a `create` envelope at sign-in and asserting 401.

## HIGH

### ACC-1 — anonymous `POST /verify-email/request` un-verifies any verified account
`security-system/.../verification/RequestEmailVerification.java:24` (also reported as TEST-1, ATK-1)

`RequestEmailVerification.execute` calls `startVerification` unconditionally and both production adapters overwrite the row with `verified=false` (`JdbcEmailVerificationRepository` delete+insert, `InMemoryEmailVerificationRepository` put). `VerifyEmailController.request` is public, throttled per IP only (5 per 15 min), never asks `isVerified`. `/register` applies the opposite rule next door (notice instead of link when verified).

**Reproduced:** register → verify → `/authenticate` 200; anonymous `/verify-email/request {email}` → 202; `/authenticate` with the same correct password → **403 EMAIL_NOT_VERIFIED**. One request per victim per window keeps them out. No JVM or browser test forbids the path; the browser glue actually exercises it and passes because the fresh link re-verifies. Secondary: after the flip a federated squatter takeover (`FederatedSignIn.claimByEmail`) becomes reachable for an unlinked provider identity.

**Fix (system layer):** return early in `RequestEmailVerification.execute` when `repository.isVerified(email)` (no token, no mail). Add an HTTP test next to `RegisterEnumerationHttpTest` and a rule in `verify-email.feature` ("requesting VERIFICATION for an already verified EMAIL changes nothing"). Note the browser glue's shared step "a registered USER" verifies the account, so verify-email Rule 1 in the UI harness must seed with the existing "whose EMAIL is not verified yet" step.

### ACC-2 — `RequestEmailChange` bypasses the e-mail domain policy (blocked / disposable / company)
`security-system/.../account/RequestEmailChange.java:30`

Only `Register` runs `_EmailVerdict.judge` against `CanRegisterConfig`. `RequestEmailChange` checks uniqueness only and is wired without the policy (`BeanFactory.java:553-557`); `ConfirmEmailChange` moves the account and marks the new address verified without re-judging. Nothing in `change-email.feature`, tests or docs declares the policy registration-only.

**Reproduced** with `security.email.company.domains=acme.com`, `disposable.domains=mailinator.com`: `/register x@mailinator.com` → 422; `bob@acme.com` registers, steps up, `/account/email/request {bob@mailinator.com}` → 202; confirm → 200 EMAIL_CHANGED; `/authenticate bob@mailinator.com` → **200**. Roles, factors and federated links follow the account. Impact is conditional on a deployment configuring at least one list (compose configures none), but for a closed-shop deployment the membership gate is bypassable after first login.

**Fix (system + infrastructure):** give `RequestEmailChange` the `CanRegisterConfig` and run the same judge before `existsBy` (a package-private `_NewEmailVerdict` step in `account`, per ADR 0002, or a shared judge step); new `RequestEmailChangeResult.Rejected(codes, policy)`; `BeanFactory#requestEmailChange` passes `emailPolicy(environment)`; `EmailChangeController` maps `Rejected` → 422 with the `/register` error shape. One `RequestEmailChangeTest` example with a blocked domain and one rule in `change-email.feature` with a literal domain (Rebuild-level sample).

### ATK-4 — `POST /account/password` is an unthrottled Argon2 oracle for the current password
`security-system/.../account/ChangePassword.java:49`

Reachable with nothing but a live (possibly stolen) access token; runs a full Argon2 verify of the client-supplied `currentPassword` and answers 400 WRONG_CURRENT_PASSWORD on a miss. No `SourceThrottle`, no step-up elevation (change-password was removed from the `StepUpAction` catalogue in `1929cb4` on the premise that the inline verify was protection), no `LockoutSubject` accounting. On a hit the password changes and `revokeAllSessions` evicts the owner: a time-boxed session theft becomes persistent takeover. Each guess also costs a full Argon2 on the blocking executor (CPU-exhaustion vector).

**Reproduced:** 40 wrong guesses on one token → 40 × 400, 0 × 429/403, ~133 ms per guess; guess 41 with the real password → 200 PASSWORD_CHANGED.

**Fix (infrastructure, minimal):** a `@Named("change-password") SourceThrottle` in `BeanFactory` (mirroring step-up) injected into `ChangePasswordController` with the same `throttled()` shape (429 + Retry-After). More complete: restore `CHANGE_PASSWORD` to the step-up catalogue and guard with `StepUpGuard`; optionally route misses through the same `LockoutSubject` accounting as `Authentication` so guessing is capped per account. Add a `change-password.feature` rule for the limit. `docs/mfa-design.md:170,246` and `docs/opus-playbook.md:80` still list change-password under step-up — realign whichever way this goes.

### AUTH-2 — the second factor has no rate limit: a password holder brute-forces TOTP / e-mail codes
`security-system/.../authentication/ContinueAuthentication.java:14` (also ATK-3)

`/authenticate` has no `SourceThrottle` and a correct password *clears* the (source, account) pair instead of counting, so an attacker holding the password opens unlimited MFA tickets; `/authenticate/factor` gives `CodeMaxAttempts` (5) wrong proofs per ticket with no per-source throttle and no brute-force accounting. The javadoc on `ContinueAuthentication` and `docs/mfa-design.md:100-102` promise throttling that no code performs; the owner throttled the identical threat on `/account/step-up` but not here.

**Reproduced:** 30 tickets, 150 wrong proofs, 0 × 429, 30 codes mailed, pair still unblocked, real code then signs in; on the same pair 4 wrong *passwords* do block. Consequences: TOTP guessable at 3 valid codes per 30 s window bounded only by one Argon2 per 5 guesses; with EMAIL/SMS every ticket sends a fresh code, so the loop is a mail/SMS bomb on the victim.

**Fix (infrastructure):** a `@Named("authentication") SourceThrottle` (`security.authentication.max-per-window`, `window-minutes`, 0 disables; 0 in the test profile, raised in compose like registration) applied in `AuthFactorController` and `AuthenticationController` before the use case. Optionally (system layer, owner's call): store the `Source` in `PendingAuthentication` and charge wrong proofs through `_UpdateBruteForceRecords` on the same `LockoutSubject`, making the javadoc true. HTTP test for the N+1th `/authenticate/factor` → 429; rule in `mfa.feature` "a wrong proof counts like a wrong password" — or delete the promise from the javadoc and the design doc.

### AUTH-3 — sessions survive an e-mail change and re-bind to whoever registers the freed address
`security-system/.../account/ConfirmEmailChange.java:83` (also ACC-3, DB-2, ATK-2)

`ConfirmEmailChange` moves or purges every address-keyed store except sessions. Sessions carry only the address, so after the change every pre-existing session still authorizes as `old@`, refresh keeps rotating it, "Sign out everywhere" / reset / delete under the new address (`revokeAllSessions(new@)`) never reach it, and `GET /sessions` under the new address does not list it. Immediately after the change the stale caller has no user row and falls back to `[USER]`; the old address is free the moment `updateEmail` runs, and once someone registers it, the stale session's roles (`/me`, JWT claims), session list and revoke-all resolve to the **newcomer's** account. `AddressKeyedStoresTest` excludes sessions from the move law and calls the gap "reported", but no todo item or branch carries it.

**Reproduced** at use-case level with the production in-memory adapters (10-step trace in the run log: authorize(phone) = old@ after the change and after revokeAll(new@); refresh succeeds; old@ free; after Mallory registers old@, the phone's caller resolves to Mallory's roles and session list).

**Fix (system layer):** give `ConfirmEmailChange` an `AuthorizationDataRepository sessions` and call `sessions.revokeAllSessions(change.currentEmail())` right after `updateEmail` — the same price `ChangePassword` and `ResetPassword` already charge. `BeanFactory#confirmEmailChange` passes it. `ConfirmEmailChangeTest` gets the mock and one example; `AddressKeyedStoresTest` can drop the "deliberately NOT in the registry" paragraph; `change-email.feature` gets one rule. Re-keying sessions to `users.id` is the long-term fix.

### DOM-1 — a User-Agent longer than 400 chars turns every wrong guess into a 500 that records no failure, so the lockout never trips
`security-domain/.../vo/Source.java:15`, adapter `JdbcRejectedAuthenticationRepository.create` (also DB-1)

`Source.userAgent` is unbounded, the HTTP adapter passes the raw header through, the JDBC adapter writes it into `user_agent VARCHAR(400)` (V9). PostgreSQL refuses the INSERT (22001), the `DataAccessException` escapes the transactional boundary uncaught, the request answers 500 with the SQL error in the body, and no failure row is written. The brute-force guard counts only those rows and nothing else rate-limits `/authenticate`.

**Reproduced** against PostgreSQL 18 via Testcontainers: every wrong guess with a 401+ char User-Agent → 500 `value too long for type character varying(400)`, rows stay 0; a 400-char UA → 401 and counts; the correct password with a 401-char UA takes the Valid branch (never touches the column) and is distinguishable. In-memory adapter has no column, so all specs stay green; no test sends a User-Agent at all.

**Fix (infrastructure, JDBC adapter):** clamp in `JdbcRejectedAuthenticationRepository.create` to the column width (`USER_AGENT_COLUMN_WIDTH = 400`, comment pointing at V9) — the adapter is the one place that knows the table's shape, and this keeps `Source` untouched. One `JdbcAdaptersTest` case with a 1000-char user agent asserting the count rises; optionally an HTTP assertion that a long UA with a wrong password is 401, not 5xx.

### HTTP-1 — behind a trusted proxy the *leftmost* X-Forwarded-For element is the source: brute-force key and every throttle become client-chosen
`security-infrastructure/.../ClientIpResolver.java:40` (also AUTH-8, ATK-5)

When the peer is in `security.trusted-proxies`, the resolver takes `X-Forwarded-For[0]` — the element the client wrote whenever the proxy *appends* (nginx `$proxy_add_x_forwarded_for`, ingress-nginx, Traefik, any LB→ingress chain). That value keys all four `SourceThrottle`s and the `LockoutSubject`, so the client rotates it and is never throttled or blocked, or writes a victim's address to pre-fill the victim's failure window. Dormant today (`trusted-proxies` is set nowhere), but `portal/PLAN-P12.md` K1 — the first planned deployment step — tells the deployer to set it, and arms this. Also: `trustedProxies.contains(remoteAddress)` is an exact-string match, so the CIDR K1 prescribes would match nothing.

**Reproduced** with loopback declared trusted: `/register` with max-per-window=1 and header `10.0.0.N, 9.9.9.9` (rotating head) → 201, 201, 201; fixed head → 201, 429, 429; `/authenticate` wrong password × 6 with rotating head → 401 × 6, no block; control without trusted-proxies → header ignored.

**Fix (infrastructure, one class):** walk X-Forwarded-For from the **right**, skip every element that is a trusted proxy, return the first untrusted one (rightmost-untrusted); fall back to the remote address when the list is empty or all trusted; validate the candidate with `IpAddressValidator.isValid` and fall back on garbage (this also closes HTTP-2). One HTTP test booting with `security.trusted-proxies=[127.0.0.1, ::1]`. Fix together with K1, never K1 alone; either accept CIDRs or have K1 name pod IPs.

### OPS-1 — Dependabot auto-merge gates on branch *name* only: a fork PR named `dependabot/*/patches-*` gets merged into main
`.github/workflows/dependabot-auto-merge.yml:34`

The job merges any open PR whose head branch matches `dependabot/` + `/patches-` as soon as a `pull_request` CI run for that branch succeeds — no check of who opened it or where the branch lives. Verified read-only against live GitHub: repo is public and forkable, no branch protection, no rulesets, fork-approval policy `first_time_contributors`; a fork run's `head_branch` is the bare branch name (checked on a real fork run in another repo); `gh pr list --head <name>` selects cross-repository PRs; `workflow_run` jobs run with the base repo token (`contents: write`). The workflow is live (PRs 25/28/30/31 merged by github-actions). An outside account with any prior merged PR lands arbitrary commits on main unattended; a first-timer needs one "approve and run" click on a run whose branch pretends to be Dependabot's.

**Fix (CI only):** add to the job `if`: `github.event.workflow_run.actor.login == 'dependabot[bot]' && github.event.workflow_run.head_repository.full_name == github.repository`. Use `actor.login`, not `triggering_actor` (on an approved fork run the latter is the approver). Belt and braces in the step: `gh pr list ... --author app/dependabot` and `gh pr view --json author,isCrossRepository` before merging.

### UI-1 — after Sign out the sign-in form still holds the previous user's e-mail **and password**
`security-ui/src/App.tsx:591`

`password` is App state cleared only by a successful reset; `signIn` leaves it in state on both success branches; `signOut()` (also reached from "Sign out everywhere" and account deletion) clears token/me/roles/factors but not email or password. The sign-in screen is a controlled form bound to that state, so the next tab occupant sees the previous address and masked password and one submit re-posts them. Server-side session is correctly revoked; the defect is purely client-side retention. Nothing exercises sign-out (no glue, no vitest).

**Fix (UI):** `setPassword('')` once `/authenticate` has answered (both branches) and in `signOut()` together with `currentPassword`, `newPassword`, `deletePassword`, `enrolStepUpPassword`. One vitest next to `App.deletion.test.tsx` clicking `sign-out` and asserting the password input is empty.

### UI-2 — recovery codes of the previous user stay on screen for the next sign-in in the same tab
`security-ui/src/App.tsx:302`

`recoveryCodes` is set only by `generateRecoveryCodes` and cleared by nothing (`signOut`, `switchTo`, `enterSession`, `loadFactors` never touch it); `AccountScreen` shows the plain codes and hides the generate button whenever the array is non-empty.

**Reproduced** with a temporary vitest (jsdom, fetch stubbed): after Alice generates codes and signs out, Bob's account screen shows "You are bob@example.com" together with Alice's codes and no generate button. Each code still only works after Alice's password step, so this is credential disclosure to the next tab user, not an unconditional takeover. Other per-account panel state (`deleting`, `deletePassword`, `deleteTicket`, enrol step-up fields, `sessions`) survives sign-out the same way.

**Fix (UI):** a `clearAccountState()` resetting recovery codes and the per-account panel state, called from `signOut()` and at the top of `enterSession()`.
